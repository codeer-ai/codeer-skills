# Audience-Value Narrative Examples

Use these examples to understand the relationship being tested. Do not reuse
their wording mechanically or treat the examples as a fixed Codeer pitch.

## Feature inventory to operational change

Feature-first:

> Codeer combines Prompt, Knowledge Base, Eval, and version management to build
> controllable, verifiable, continuously improving Agents.

Audience-first:

> The team first uses its own cases to decide which answers are acceptable and
> which must go to a person. Only a version that passes those checks reaches the
> next scope of use. Codeer keeps the cases, decisions, and changes in one
> traceable workflow.

Why the revision is stronger:

- It names an actor, artifacts, decisions, and release condition.
- The internal mechanisms remain inferable without carrying the opening.
- Control and validation support the risk claim instead of substituting for the
  value claim.

## Click narration to a complete demo beat

Click narration:

> Next, open Eval, create a test case, run the model, and inspect the score.

Complete beat:

> This reply states the refund condition incorrectly. The supervisor keeps it as
> a case the Agent must pass. Before releasing the next version, the team reruns
> the same cases to confirm that the correction did not break answers that were
> already acceptable.

The visible product action matters because it changes a release decision. It
does not by itself prove a conversion lift, time saving, or financial outcome.

## Abstract trust to risk-specific proof

Abstract:

> Every enterprise needs full control and continuous optimization.

Risk-specific:

> Before a new version handles more conversations, the service lead can inspect
> which cases improved, which regressed, and which still require human handling.

Keep `control` as the main value only when the audience is actually responsible
for governance, compliance, or release approval. For example:

> Every model change must be rerunnable against the approved cases, attributable
> to a version, and released only after the designated reviewer approves it.

Here release control is the audience's job, so the control-first framing is a
valid exception rather than an architecture-led slogan.

## Generic CTA to verification CTA

Generic:

> Book a demo to see how Codeer improves service efficiency.

Verification-oriented:

> Bring a small set of anonymized conversations that your team finds difficult.
> We will turn one judgment workflow into a reviewable Agent and inspect together
> which cases it can handle, which need more context, and which should remain
> with a person.

The second CTA specifies the claim, test material, and observable decision. It
does not promise an unsupported outcome.

## Framework-first exception

Do not force a lived-reality opening when a declared technical audience already
accepts the stakes and is comparing architectures. A security review can begin
with data boundaries or release controls when those are the explicit decision
criteria. Record the accepted premise and keep the technical view tied to the
decision; do not insert a generic pain scene merely to satisfy a template.

## Terminology test

Do not ban Codeer terms. Introduce them after the workflow is understandable:

- `Prompt`: the instruction and decision boundary the Agent follows;
- `Eval case`: a retained situation and expected judgment used to check a
  version;
- `Version`: a named release candidate whose behavior can be compared;
- `Trace`: the record used to inspect how a result was produced.

These are examples, not mandatory translations. Adapt the language to what the
declared audience already knows and what decision it must make.
